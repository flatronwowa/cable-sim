# cable-sim

Инженерная симуляция физического кабеля в Godot: XPBD-солвер на C++ через GDExtension.

## Версии и окружение

| Компонент | Версия | Примечание |
| --- | --- | --- |
| Godot | 4.5.2-stable | `/Applications/Godot.app`, в PATH как `godot` |
| godot-cpp | ветка `4.5` (submodule) | API 4.5.0, `compatibility_minimum = "4.5"` |
| SCons | 4.11.1 | `brew install scons` |
| Компилятор | Apple clang 21 | macOS arm64 |

Версию Godot не обновлять без синхронного обновления submodule `godot-cpp`: ветки `4.6`/`4.7`
в godot-cpp не существует, поэтому переход на более новый движок потребует плавающего `master`.

## Сборка

```bash
scons target=editor -j8          # обязательно для работы в редакторе
scons target=template_debug -j8  # для экспорта debug-сборки
```

Первая сборка ~5 минут (компилируются биндинги), последующие — секунды.

Сборка `target=template_debug`, загруженная в редактор, роняет Godot в
`EditorHelp::_gen_extensions_docs()`. В редакторе используется только `target=editor`.

После изменения C++ нужно перезапускать редактор: GDExtension не перезагружается на горячую.

## Известная проблема: headless-импорт падает

`godot --headless --path project --import` роняет движок с SIGSEGV в
`EditorHelp::_gen_extensions_docs()`, как только в проекте есть GDExtension. Проверено на
Godot 4.5.2: на пустом проекте импорт проходит, с расширением — падает; линковка doc_data
проблему не снимает. Это баг headless-редактора, а не нашей сборки.

GUI-редактор и runtime при этом работают штатно. Для проверки расширения без GUI использовать
режим запуска, а не импорт:

```bash
godot --headless --path project --script some_script.gd
```

Вывод: не строить CI на `--import`, пока баг не исправлен апстримом.

## Структура

```
src/solver/    чистый C++, без единого include из godot_cpp
src/nodes/     Godot-ноды, единственный слой, знающий про движок
project/       Godot-проект, bin/ содержит .gdextension и собранные библиотеки
docs/SPEC.md   полное задание
```

## Архитектурные правила

**Солвер не зависит от Godot.** В `src/solver/` запрещены типы и вызовы движка, включая
`PhysicsDirectSpaceState3D`. Коллизии считаются своими примитивами (sphere/capsule/box/plane,
далее SDF). Причина: запросы к физике движка на каждую частицу на каждом substep — это
неприемлемый оверхед, а зависимость от движка делает солвер неотлаживаемым.

**Спейсы не смешиваются.** Солвер целиком работает в world space. Преобразование центральной
линии в local space выполняется только на границе рендеринга, при построении меша.

## Приоритеты при конфликте требований

1. Кабель не проходит сквозь collision geometry
2. Сохранение физической длины
3. Численная устойчивость
4. Корректный bending
5. Устойчивые resting contacts
6. Реалистичное трение
7. Качество меша
8. Производительность
9. Дополнительные возможности

Пункт 1 не решается способом, разрушающим пункты 2–5. При этом пункт 1 реализуется через
swept collision и substeps, то есть расходует бюджет производительности — перф здесь является
ограничением, а не последней заботой.

## Комментарии в коде

Короткие содержательные комментарии только для сложной математики: смысл constraint, где
применяется XPBD compliance, зачем нужна lambda, почему нужен конкретный collision pass, что
делает bending formulation. Для неочевидных формул указывать название метода или алгоритма.
Очевидные строки не комментировать.

## Вне области задачи

Автоматические тесты и отдельные тестовые сцены не добавляются.
